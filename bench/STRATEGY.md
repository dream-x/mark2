# mark2 bench — стратегия

## Зачем

Не академический SWE-bench, а практический инструмент под два вопроса:

1. **Выбор модели**: какая локальная модель (и с какими настройками) даёт рабочего агента на реальных мини-задачах — и насколько она хуже облачной планки.
2. **Регрессия харнеса**: фаза 2 будет менять edit-стратегии, промпт, кэш, toolshim — бенч показывает, стало лучше или хуже. Прогон бенча = приёмка изменений харнеса.

## Матрица моделей (v1)

| Алиас | Модель | Где | Роль |
|---|---|---|---|
| `qwen9` | qwen3.5:9b | localhost:11434 | быстрый бейзлайн |
| `oss20` | gpt-oss:20b | localhost:11434 | средний локальный |
| `qwen27` | qwen3.8:27b | **white.local:11434** | основной кандидат |
| `oss120` | gpt-oss:120b-cloud | localhost:11434 → Ollama Cloud | верхняя планка |

Резерв: qwen-coder-next-64k:latest (79.7B, медленный — гонять точечно). Позже: frontier-API через OpenRouter как reference ceiling (тот же провайдер-код).

Вторая ось (фаза 2): `edit_strategy` search_replace ↔ whole_file, `cache_prompt` on/off, вариации промпта. Оси не перемножаем вслепую: базовая сетка = модели × дефолтные настройки; настройки сравниваем на 1–2 моделях.

## Принципы задач

- **Агентные**: каждая требует тул-коллов, а не одного ответа.
- **Программная верификация**: у задачи есть `verify.sh` (exit 0 = pass) — никакого «на глаз». Проверяем артефакты (файлы, вывод скриптов), не точный текст ответа модели.
- **Герметичность**: фиксированный `setup/`, на каждый прогон — свежая tmp-копия; сеть задачам не нужна.
- **Диагностичность**: каждая задача изолирует одну способность. Провал T03 при прошедшем T01 = проблема именно в точности edit, а не в tool calling вообще.
- **Градиент сложности**: от одного tool call до 5–10-шаговых цепочек — видно, на каком этаже модель ломается.

## Задачи v1 (8 штук)

| ID | Задача | Проверяемая способность | Verify |
|---|---|---|---|
| T01 `create-file` | создать файл с точным содержимым | базовый tool call (write) | файл и байты совпадают |
| T02 `read-answer` | прочитать конфиг, ответить значением поля; файлы не менять | read + ответ; сдержанность | подстрока в stdout, setup нетронут |
| T03 `edit-exact` | точечная правка функции (заменить условие/константу) | точность edit (search/replace) | скрипт-проверка поведения + остальной файл нетронут |
| T04 `fix-bug-test` | «сделай, чтобы `python3 test.py` проходил» — файл с багом + тест | контур верификации: запусти → почини → перепроверь | `python3 test.py` |
| T05 `multi-file-rename` | переименовать функцию и все использования в 2 файлах | связные правки нескольких файлов | grep старого имени пуст + запуск проходит |
| T06 `search-code` | мини-репо из 6 файлов: «найди, где определяется X и что вернёт при Y» | навигация (bash/grep + read), reasoning | подстрока-ответ в stdout |
| T07 `bash-pipeline` | посчитать TODO в src/ и записать число в report.txt | bash-компетентность, композиция шагов | точное число в файле |
| T08 `write-run-script` | написать скрипт, запустить, убедиться в выводе | генерация кода + самопроверка через bash | запуск скрипта даёт эталонный вывод |

Позже (v2): T09 `long-context` (файл 2–3к строк — точечный фикс; + режим с малым context_limit → проверка компакции в бою), T10 `restraint` (поменять одно поле YAML, остальное байт-в-байт — ловит любовь малых моделей переписывать всё), T11 `permission-deny` (задача с ReadOnly — модель должна корректно отработать отказ, а не зациклиться).

Формат задачи в репе:

```
bench/tasks/T04-fix-bug-test/
├── prompt.md      # текст задачи (то, что уходит в mark2 позиционным аргументом)
├── setup/         # файлы, копируются в tmp-cwd прогона
├── verify.sh      # exit 0 = pass; запускается в tmp-cwd после прогона
└── task.toml      # timeout_seconds, repeats-override, теги
```

## Протокол прогона

- **Последовательно**, не параллельно: модели делят RAM/GPU, параллель врёт в таймингах.
- **Прогрев**: 1 холостой запрос модели перед таймингами (загрузка в память не считается).
- **Повторы**: 3 на пару модель×задача (агентные прогоны недетерминированы) → pass rate + медианы.
- **Температура 0** у всех (сравниваем модели, не сэмплинг), `--policy yolo`, `-p` print mode.
- **Таймауты** по классу: 9b — 120с, 20–27b — 300с, cloud — 300с (из task.toml × множитель модели).
- **Сессии** пишутся и складываются в артефакты прогона — это источник глубоких метрик.

## Метрики

Из exit code + stderr + session JSONL (наш формат уже пишет всё нужное):

- `pass` (verify.sh), **pass rate** по повторам;
- wall time (медиана);
- tokens in/out (стоимость — критично для cloud);
- сэмплинг-итераций на ход (лишние круги = слабое планирование);
- tool-коллов всего и **tool error rate** (доля is_error результатов — кривые аргументы, промахи edit; главный индикатор качества tool calling у малых моделей);
- обрывы/таймауты отдельной строкой.

## Выход

`bench/results/<дата>-<label>/`: `results.json` (сырьё), `report.md` (таблица модель×задача: ✓/✗, медиана времени, токены; сводка pass rate + tool error rate), `sessions/` (JSONL). В git коммитим `report.md` + `results.json`, sessions — в .gitignore.

## Известные грабли

- На `localhost:8080` живёт посторонний сервис — base_url всегда указывать явно.
- Ollama Cloud (`*-cloud`) требует залогиненного локального ollama; тарифицируется — следить за tokens out.
- Ollama выгружает модели по keep_alive — между задачами одной модели не давать ей выгрузиться (или учитывать в прогреве).
- qwen3.8:27b на white — сеть добавляет латентность первого байта; сравнивать TTFB некорректно, только полное время задачи.

## Чего сознательно нет в v1

Ранер решён и написан: **Rust**, крейт `crates/bench`, бинарь `mark2-bench` (`cargo run -q -p mark2-bench -- --help`) — тот же workspace и те же типы сессий из `mark2-core`, без второй экосистемы ради скрипта. Сознательно нет: LLM-judge-оценок (только программная верификация), параллельных прогонов, статистики глубже медианы, CI-интеграции.
