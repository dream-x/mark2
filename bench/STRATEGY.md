# mark2 bench — стратегия

## Зачем

Не академический SWE-bench, а практический инструмент под два вопроса:

1. **Выбор модели**: какая локальная модель (и с какими настройками) даёт рабочего агента на реальных мини-задачах — и насколько она хуже облачной планки.
2. **Регрессия харнеса**: фаза 2 будет менять edit-стратегии, промпт, кэш, toolshim — бенч показывает, стало лучше или хуже. Прогон бенча = приёмка изменений харнеса.

## Матрица моделей (v1)

| Алиас | Модель | Где | Роль |
|---|---|---|---|
| `qwen9` | qwen3.5:9b | localhost:11434 | быстрый бейзлайн |
| `oss20` | gpt-oss:20b | localhost:11434 | средний локальный |
| `qwen27` | qwen3.8:27b | **white.local:11434** | основной кандидат |
| `oss120` | gpt-oss:120b-cloud | localhost:11434 → Ollama Cloud | верхняя планка |

Резерв: qwen-coder-next-64k:latest (79.7B, медленный — гонять точечно). Позже: frontier-API через OpenRouter как reference ceiling (тот же провайдер-код).

Вторая ось (фаза 2): `edit_strategy` search_replace ↔ whole_file, `cache_prompt` on/off, вариации промпта. Оси не перемножаем вслепую: базовая сетка = модели × дефолтные настройки; настройки сравниваем на 1–2 моделях.

## Принципы задач

- **Агентные**: каждая требует тул-коллов, а не одного ответа.
- **Программная верификация**: у задачи есть `verify.sh` (exit 0 = pass) — никакого «на глаз». Проверяем артефакты (файлы, вывод скриптов), не точный текст ответа модели.
- **Герметичность**: фиксированный `setup/`, на каждый прогон — свежая tmp-копия; сеть задачам не нужна.
- **Диагностичность**: каждая задача изолирует одну способность. Провал T03 при прошедшем T01 = проблема именно в точности edit, а не в tool calling вообще.
- **Градиент сложности**: от одного tool call до 5–10-шаговых цепочек — видно, на каком этаже модель ломается.

## Проектный тир (T17)

Не одна способность, а целый проект: T17 `ws-chat` — чат на вебсокетах (aiohttp-бэкенд,
vanilla JS-фронт) плюс собственный автотест модели `test_chat.py`. Контракт (файлы,
протокол, id элементов, «никакого авто-джойна») прибит в `prompt.md`, setup пустой.

**Почему verify в несколько слоёв.** 2026-11-03 flint:40b собрал такой чат, его
скриптовый смоук протокола (два ws-клиента) был зелёным, а UI мёртв: `app.js` в
`ws.onopen` сам джойнился как `anon` и дизейблил `#nick`/`#join-btn` — нашлось только
руками в браузере. Поэтому `verify.sh` гоняет три независимых слоя, каждый на своём
свежем `server.py` на свободном порту (`PORT` из env):

| Слой | Чем | Что ловит |
|---|---|---|
| A protocol | `checks/protocol.py`, aiohttp ws-клиенты | history на join, system на join/leave, броадкаст всем включая отправителя, история новичку, лимит 50 |
| B ui | `checks/ui.py`, Playwright + headless Chromium, пробный ws-клиент | авто-джойн при загрузке, недоступный `#nick`, Enter/клик для join и send, рендер истории и входящих |
| C own test | `checks/own_test.py` | `python3 test_chat.py` модели проходит за 60 с (дисциплина самопроверки; тривиальный тест тоже пройдёт — истина за A/B) |

Слои идут все, даже если один упал: вердикты по слоям — в stdout verify (переживают
обрезку stderr), подробности — в stderr. Доказательство, что B добавляет сигнал, —
`selftest/run.sh`: golden → PASS; `buggy-ui` (сегодняшний баг) → A PASS, B FAIL;
пустая директория → FAIL на файлах; `crash` (server.py не компилируется) → FAIL про
сервер. Прогонять после любой правки чекеров: `sh bench/tasks/T17-ws-chat/selftest/run.sh`.

**Окружение verify — `bench/uitest/`.** `bootstrap.sh` собирает `bench/uitest/.venv`
(в .gitignore) из `requirements.txt` (aiohttp + playwright, версии запинены: 1.64.x ↔
chromium-1248 из `~/Library/Caches/ms-playwright`) и делает `playwright install chromium`
+ смоук запуска браузера. Готовый venv помечен штампом с cksum requirements —
повторный вызов мгновенный, недостроенный или устаревший пересобирается с нуля.
Для задачи с `uitest_env = true` bootstrap зовёт ранер — один раз до прогрева первой
модели; провал останавливает бенч сразу (с хвостом вывода и командой
`sh bench/uitest/bootstrap.sh --force`), а не съедает таймаут задачи у каждой модели.
`verify.sh` зовёт bootstrap и сам (под ранером — мгновенно, при ручном запуске или в
selftest — первая сборка ~30 с), при провале — FAIL [env] с той же командой. Сеть нужна
только bootstrap; сами проверки ходят лишь на 127.0.0.1 (внешние запросы страницы
браузер обрывает).

**Окружение модели — интерпретатор `bench/uitest/.venv`.** `uitest_env = true` в
task.toml: ранер кладёт в песочницу прогона директорию `python-bin/` ровно с одним файлом
`python3` — обёрткой `exec '<abs>/bench/uitest/.venv/bin/python3' "$@"` — и запускает
mark2 с ней первой в `PATH`. `python3` модели — тот же интерпретатор с aiohttp, которым
verify потом гоняет её `server.py` и `test_chat.py` (и `sys.executable` в её тесте
указывает туда же). Прогрев и задачи без поля получают `PATH` ранера как есть. Зачем: на
бенч-машине `python3` из PATH — голый pyenv без aiohttp; 2026-11-04 (прогон t17-v1)
qwen3.6 потратила большинство из 14 ходов за час на `python3 -m venv .venv && pip install
aiohttp` / `pip3 install --break-system-packages aiohttp`, команды умирали по таймауту
bash 120 с на занятой сети, прогон кончился общим таймаутом — мерили сеть до PyPI, а не
постройку проекта. Промпт теперь говорит «`python3` on your PATH has aiohttp available»
и не разрешает ставить пакеты; сеть модели не нужна.

Почему одна обёртка, а не весь `.venv/bin`: там же лежат `pip` и прочие бинари venv, и
`pip install` модели менял бы окружение, которым verify судит все прогоны. Теперь голый
`pip`/`pip3` модели — тот, что в `PATH` ранера (как до uitest_env, промпт запрещает ставить
глобально). Почему обёртка, а не симлинк: venv узнаёт себя по `pyvenv.cfg` рядом с
*запущенным* путём, и симлинк из чужой директории поднимает базовый интерпретатор мимо
venv (проверено: `sys.executable` = homebrew python3.14, aiohttp не из venv). Директория
своя у каждого прогона и уходит вместе с песочницей — сломать её для следующих прогонов
модель не может. Остаток риска: `python3 -m pip install …` всё ещё идёт в venv verify —
полностью его закрывает только read-only venv (частично — `PIP_NO_INDEX=1` в окружении
mark2), пока не делаем.

**Настройки задачи** (per-task поля task.toml): `max_turns = 80` — дописывается
в `[agent]` генерируемого `.mark2.toml` (дефолт агента 50, flint:40b в него упёрся);
`verify_timeout_seconds = 300` — свой бюджет verify вместо общих 30 с (три слоя);
`uitest_env = true` — см. выше; `timeout_seconds = 1800`.

Гонять отдельно: `cargo run -p mark2-bench -- --tasks T17 --repeats 1`.

## Тир ревью (T20–T21)

Меряет модель не как исполнителя, а в роли ревьювера `scripts/review.sh`: промпт задачи —
ровно то, что обёртка отдаёт mark2 (инструкция `prompts/review.md`, diff stat и дифф с
номерами строк нового файла), `policy = "read-only"` (у обёртки — `--policy read-only`),
температура 0 (дефолт и обёртки, и бенча). Обе задачи — на одном мини-проекте без
зависимостей (Python: `lib/pager.py`, `report.py`, `cli.py`, `tests/test_pager.py`);
`setup/` — рабочее дерево после правки (как его видит `git diff HEAD`), сам дифф есть
только в промпте. Пара читается вместе: ревьювер, который на всё отвечает needs-work
(или на всё approve), набирает ровно половину, годный — обе. Гонять отдельно:
`--tasks T20,T21`.

| ID | Задача | Ловушка | Проверяемая способность |
|---|---|---|---|
| T20 `review-bug` | дифф переводит `page_bounds()` с `(first, last)` включительно на полуоткрытый `(start, stop)`; докстринг, `paginate()` и тесты обновлены — внутри диффа всё самосогласовано, тесты зелёные | сломанный вызыватель `report.py` в дифф не попал и в промпте не упомянут: он по-прежнему режет `rows[first:last + 1]`, каждая страница прихватывает первую строку следующей (на леджере из 45 строк с суммами 1..45 подытоги дают 1097 при итоге 1035) | recall: заметить смену контракта и найти вызывателей поиском (`grep page_bounds`); verify: последний вердикт needs-work и в ответе назван `report.py` (в промпте его нет — назвать можно, только найдя поиском); якорь `файл:строка` находки и severity не проверяются |
| T21 `review-clean` | тот же проект до правки T20; дифф сравнимого размера: переименование локальной, `page < 1 or page > count` → `not 1 <= page <= pages`, перефразированный докстринг (контракт тот же), переименования в тесте | поведение не меняется — `report.py`, `cli.py` и тесты дают байт-в-байт тот же вывод, `check_page()` покрыт тестами с обеих сторон диапазона; соблазн выдумать находку ради вердикта | precision: не шуметь на чистом диффе; verify: последний вердикт approve, больше ничего |

**`prompt.md` заморожен и руками не пишется.** Его делает `regen.sh` в каталоге задачи:
копирует `setup/` в scratch git-репо, откатывает вшитый патч (`git apply -R`) и коммитит
«до»-версию, накатывает патч обратно, сверяет дерево с `setup/` и `git diff HEAD` с патчем,
гоняет настоящий `scripts/review.sh` с фейковым mark2 (`MARK2_REVIEW_BIN`, приём
`scripts/test-review.sh`), который сохраняет промпт со stdin, — он и становится
`prompt.md`; нумерация хунков — тем же awk, что в бою. Для T20 regen ещё проверяет, что
`report.py` в промпте не встречается — на этом держится критерий verify.
Правишь `prompts/review.md` или сборку промпта в `review.sh` — перегенерируй оба:
`sh bench/tasks/T20-review-bug/regen.sh && sh bench/tasks/T21-review-clean/regen.sh`
(версия, от которой сгенерено, — в шапке regen.sh), иначе бенч меряет старую инструкцию.

Вердикт verify разбирает копией `parse_verdict` из `review.sh`: побеждает последняя
строка-вердикт, markdown-обёртка и регистр прощаются; вердикта нет — FAIL. Отличия от боя:
обёртка при ответе без вердикта перезапускает модель один раз, бенч — нет (меряется один
выстрел); промпт уходит позиционным аргументом, а не через stdin; в песочнице нет `.git`
(ревьюверу он и не нужен: bash запрещён) и лежит `.mark2.toml` ранера. Инструкция
говорит про «Rust agent harness» и `#[cfg(test)]`, а проект на Python — оставлено
сознательно: меряем боевую инструкцию как есть, а не идеальный промпт.

Критерий T20 ослаблен после первой матрицы (`20261104-175213-review-v1`): вначале verify
требовал ещё ссылку `lib/pager.py:N` в изменённом хунке, но модели, нашедшие баг, якорят
находку на сломанном вызывателе (`report.py:38`) — это семантически верно, а verify их
валил: по нему recall был 1/12 при реальном 4/12 (glm52 3/3, qwen36c 1/3); новый verify
на тех же ответах даёт 4/12.

Самопроверка verify (2026-11-04, синтетические ответы без модели, под sh и dash, 24
случая): T20 PASS — правильный ответ, вердикт в `**…**`/`` `…` ``/`## **Verdict:**`/CRLF,
approve и затем needs-work, needs-work + `report.py` вовсе без строки-находки, находка с
якорем на `report.py:38`; FAIL — approve, approve при найденном баге, needs-work без
`report.py`, needs-work только за пробел в тестах, нет вердикта, пустой ответ,
`VERDICT: approved`, `needs work` через пробел, needs-work и затем approve.
T21 PASS — approve (в т.ч. `**Verdict:** Approve` и с minor-находкой); FAIL — needs-work,
нет вердикта, `approved`, approve и затем needs-work.

Формат задачи в репе:

```
bench/tasks/T04-fix-bug-test/
├── prompt.md      # текст задачи (то, что уходит в mark2 позиционным аргументом)
├── setup/         # файлы, копируются в tmp-cwd прогона
├── verify.sh      # exit 0 = pass; запускается в tmp-cwd после прогона
└── task.toml      # timeout_seconds, repeats-override, теги
```

## Протокол прогона

- **Последовательно**, не параллельно: модели делят RAM/GPU, параллель врёт в таймингах.
- **Прогрев**: 1 холостой запрос модели перед таймингами (загрузка в память не считается).
- **Повторы**: 3 на пару модель×задача (агентные прогоны недетерминированы) → pass rate + медианы.
- **Температура 0** у всех (сравниваем модели, не сэмплинг), `--policy yolo`, `-p` print mode. Задачи с `policy = "read-only"` в task.toml (T16, T20, T21) идут с `--policy read-only`.
- **Тир ревью** (T20+T21) гоняется и читается парой: recall без precision — это ревьювер, который на всё говорит needs-work. Перед прогоном — `prompt.md` должен быть сгенерен от текущих `prompts/review.md`/`scripts/review.sh` (см. regen.sh).
- **Таймауты** по классу: 9b — 120с, 20–27b — 300с, cloud — 300с (из task.toml × множитель модели).
- **Сессии** пишутся и складываются в артефакты прогона — это источник глубоких метрик.
- **Абляция post-edit сенсора** (план): `--tasks T04,T11 --agent-override 'post_edit_command = "python3 -B test.py"'` против прогона без оверрайда, repeats ≥ 3 — обе задачи несут самопроверку `test.py` в песочнице, так что сенсор возвращает модели настоящий `AssertionError` после каждой правки.
- **Абляция** настроек mark2 — `--agent-override 'key = value'` (повторяемый): строка дописывается в `[agent]` `.mark2.toml` каждого прогона, например `--agent-override 'arg_coercion = false' --agent-override 'write_churn = false' --label ablation`. Ключ и значение проверяются парсером mark2 до первого прогона (опечатка или конфликт с `max_turns` задачи — сразу ошибка), overrides пишутся в `results.json` (`config.agent_overrides`) и в шапку `report.md`. Сколько вызовов спасло приведение типов аргументов — `· coerced N` в итоговой строке stderr каждого прогона.

## Метрики

Из exit code + stderr + session JSONL (наш формат уже пишет всё нужное):

- `pass` (verify.sh), **pass rate** по повторам;
- wall time (медиана);
- tokens in/out (стоимость — критично для cloud);
- сэмплинг-итераций на ход (лишние круги = слабое планирование);
- tool-коллов всего и **tool error rate** (доля is_error результатов — кривые аргументы, промахи edit; главный индикатор качества tool calling у малых моделей);
- **телеметрия обвязки** — сколько раз модель ловили контроли mark2, по маркерам stderr (`crates/bench/src/telemetry.rs`): нуджи `[agent] write_churn` / `[agent] loop_detection`, `· coerced N` итоговой строки, `[agent] compaction`, строки `✗ <тул>:`; per-run — `runs[].harness` в `results.json`, суммы по модели — раздел «Обвязка» в `report.md`;
- обрывы/таймауты отдельной строкой.

## Выход

`bench/results/<дата>-<label>/`: `results.json` (сырьё), `report.md` (таблица модель×задача: ✓/✗, медиана времени, токены; сводка pass rate + tool error rate), `sessions/` (JSONL). В git коммитим `report.md` + `results.json`, sessions — в .gitignore.

## Известные грабли

- На `localhost:8080` живёт посторонний сервис — base_url всегда указывать явно.
- Ollama Cloud (`*-cloud`) требует залогиненного локального ollama; тарифицируется — следить за tokens out.
- Ollama выгружает модели по keep_alive — между задачами одной модели не давать ей выгрузиться (или учитывать в прогреве).
- qwen3.8:27b на white — сеть добавляет латентность первого байта; сравнивать TTFB некорректно, только полное время задачи.

## Чего сознательно нет в v1

Ранер решён и написан: **Rust**, крейт `crates/bench`, бинарь `mark2-bench` (`cargo run -q -p mark2-bench -- --help`) — тот же workspace и те же типы сессий из `mark2-core`, без второй экосистемы ради скрипта. Сознательно нет: LLM-judge-оценок (только программная верификация), параллельных прогонов, статистики глубже медианы, CI-интеграции.
